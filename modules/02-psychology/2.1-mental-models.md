# 2.1 Mental Models

## In one line

A mental model is the user's internal belief about how a system works; almost every usability problem is a gap between that belief and the system's actual behaviour.

## Basic

Three models exist for any product:

- **The system model** — how it actually works internally (the database, the sync engine, the state machine).
- **The conceptual model** — the story the design tells about how it works ("your files live in folders").
- **The user's mental model** — what the user believes after using it.

The designer's job is to craft a conceptual model that is (a) simple enough to learn and (b) accurate enough that predictions made from it come true. The user does not need the truth. They need a model that never betrays them.

**Everyday analogy — the thermostat.** Many people believe a thermostat is a valve: set it to 30°C and the room heats *faster*. It is not; it is a threshold switch, so the room heats at the same rate either way. The false mental model persists because the interface (a dial that goes higher) suggests "more." That is a conceptual-model failure baked into the control.

## Deeper

### Norman's Gulfs

- **Gulf of Execution** — the distance between what the user wants to do and how they must express it. Symptom: "I do not know how to do this here." Bridged by discoverable, well-labelled controls and clear affordances.
- **Gulf of Evaluation** — the distance between the system's state and the user's ability to perceive and interpret it. Symptom: "Did that work?" Bridged by feedback and visible system status.

Every interaction problem you find in a usability test can be sorted into one of these two buckets. Doing that sorting out loud in an interview is a strong signal.

### Where mental models come from

1. **Prior products.** The dominant source. This is why Jakob's Law works: users spend most of their time on *other* sites and arrive with those conventions loaded.
2. **The physical world.** Trash cans, folders, sliders, cards, layers.
3. **Language.** "Archive" implies retrievable; "delete" implies gone. Naming *is* modelling.
4. **The design itself.** Structure teaches: if the settings screen groups items by internal architecture, users learn your architecture — usually badly.

### When to match vs. when to teach

Match the existing model by default. Break it only when the new model is genuinely better *and* you can afford the teaching cost. Two examples:

- **Gmail replacing folders with labels.** A better model (a message can carry many labels), and it required years of teaching. Google could afford that; a small product usually cannot.
- **Figma's multiplayer canvas.** Broke the "save your file" model. It won because the payoff was visible instantly, and because the absence of Save was reinforced with constant presence cues.

The rule of thumb: the more infrequent the task, the more you must match existing models, because users have no opportunity to learn yours.

### Model mismatches you will see constantly

| Mismatch | Symptom |
| --- | --- |
| Sync vs. save | "Where did my changes go?" |
| Archive vs. delete | Users hoard or lose data |
| Draft vs. published | Accidental publishing, or invisible drafts |
| Account vs. profile vs. workspace | Users cannot find settings |
| Cart vs. wishlist vs. saved | Items lost between sessions |

## Applications

**Product example — Apple Photos "Recently Deleted."** The real system model is deferred deletion. The conceptual model is a trash can with a countdown ("30 days"). Users' model becomes "it is recoverable for a month," which is accurate, so predictions hold and anxiety drops.

**Product example — the failed one.** Many enterprise tools expose "Save" *and* autosave. Users cannot tell which state their work is in, so they compulsively press Save. The conceptual model is incoherent because two models are visible at once. Pick one.

**Do this / not that**

- *Not that:* Naming a section after the internal service that powers it ("Identity Hub").
- *Do this:* Naming it after the user's goal ("Sign-in and security"), and running a first-click test to verify the label predicts the content.

## How to elicit a mental model in research

- **Draw-it exercises:** "Sketch how you think this works." The errors are the finding.
- **Card sorting:** open sort reveals users' grouping logic, which is a mental model in structured form.
- **"What do you expect will happen if you tap this?"** — asked *before* the tap. The gap between prediction and result is the measured mismatch.
- **Post-task recall:** "Where would you go to find that again?" Poor recall means the structure did not teach.

## Interview angle

**Common questions**
- "How do you decide whether to follow a convention or invent something new?"
- "Users keep missing this feature. Why?"
- "What is the gulf of execution?"

**How to answer the convention question.** Give a decision rule, not an opinion: "Default to the convention, because users' models are built elsewhere. I break it only if the new model is meaningfully better on a dimension the user cares about, the task is frequent enough that the learning cost is amortised, and I can add a bridge — an onboarding moment, a familiar fallback, or a visible cue that teaches the new model in place. If I cannot afford the bridge, I keep the convention."

**When they ask "why is this confusing?"** Sort the problem: is the user unable to form an intention into an action (execution), or unable to tell what happened (evaluation)? Then name a fix specific to that gulf. Most candidates jump to a fix; naming the diagnosis first reads as senior.

## Check yourself

1. Name the three models involved in any product, and say which one the designer controls directly.
2. Give a symptom sentence a user would say for each of the two gulfs.
3. What is the strongest source of a new user's mental model, and which UX law follows from that fact?
4. Name a condition under which breaking a convention is justified.
