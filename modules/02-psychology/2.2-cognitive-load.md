# 2.2 Cognitive Load

## In one line

Working memory is small and easily saturated; every element that demands thought without advancing the task is a tax on the user's ability to complete it.

## Basic

Cognitive Load Theory (John Sweller) splits load into three types:

- **Intrinsic load** — inherent difficulty of the task itself. Filing taxes is hard; no design makes it trivial. You can only *sequence* it.
- **Extraneous load** — load created by how the information is presented. Ambiguous labels, inconsistent layouts, unnecessary decisions, jargon, visual noise. **This is the designer's territory.** Reduce it aggressively.
- **Germane load** — effort that builds understanding, i.e. constructing a mental model. This is the useful kind; protect it.

The whole discipline compresses to: **minimise extraneous, manage intrinsic, protect germane.**

## Deeper

### Sources of extraneous load, ranked by how often they appear

1. **Unnecessary choices.** Every option is a decision. Defaults remove decisions without removing capability.
2. **Inconsistency.** Two buttons that look different but do the same thing force re-evaluation each time.
3. **Ambiguous language.** Internal jargon, unlabelled icons, and negated checkboxes ("Do not opt out of…").
4. **Visual noise.** Competing weights, too many type sizes, decorative dividers between already-separated things.
5. **Split attention.** Instructions in one place, the field they describe in another; a legend far from its chart.
6. **Memory carries.** Any point where the user must hold a value from screen A to use on screen B.
7. **Interruption.** Modals, tooltips, and permission prompts fired during a task, not between tasks.

### Techniques that reduce load

| Technique | What it does |
| --- | --- |
| **Progressive disclosure** | Show the common 80% first, advanced options behind a clear affordance. Cost: extra clicks for power users, so make the disclosure predictable. |
| **Chunking** | Group into meaningful units — phone numbers as 3-3-4, forms into sections with headers. |
| **Sensible defaults** | The most common correct answer, pre-filled and editable. Highest-leverage load reducer in most forms. |
| **Recognition over recall** | Show options rather than requiring memory (see 2.4). |
| **Constraints** | Prevent invalid states rather than validate them afterwards — date pickers instead of free-text dates. |
| **Inline help at the point of need** | Not a help centre link; the sentence that answers the doubt, next to the field. |
| **One primary action per screen** | Visual hierarchy that makes the next step unambiguous. |
| **Deferred complexity** | Ask for the phone number after value is delivered, not before. |

### The trade-off nobody mentions

Reducing steps per screen increases screens. A single long form and a ten-step wizard have the same intrinsic load; they differ in *perceived* load and error recovery. Wizards suit infrequent, high-stakes, branching tasks. Single pages suit frequent, familiar, short tasks — power users hate wizards because efficiency (Nielsen's second component) is what they optimise for.

**Tesler's Law** (see `03-ux-laws`) is the boundary condition: complexity cannot be deleted, only relocated — to the system, the designer, or the user. The design question is always *who absorbs it*.

### Measuring load

- **NASA-TLX** — self-reported workload across six dimensions; useful pre/post redesign.
- **Single Ease Question (SEQ)** — one 7-point item after each task. Cheap, surprisingly sensitive.
- **Time on task + error rate** — behavioural proxies.
- **Pupillometry / eye-tracking** — precise, expensive, rarely worth it outside research labs.
- **Hesitation in session recordings** — free, directional: cursor circling is a load signal.

## Applications

**Example — Google's homepage.** One field, one implicit action. Everything else deferred. The intrinsic task (express an information need) is untouched; the extraneous load is near zero.

**Example — a load-heavy pattern.** A booking form asking for passport number, issuing country, and expiry before the user has chosen a fare. All three are required *eventually*; requiring them *now* forces the user to fetch a physical document mid-decision. Reordering alone can move conversion materially.

**Do this / not that**

- *Not that:* A settings page with 40 toggles, alphabetised.
- *Do this:* Six groups with plain-language headers, the four most-changed settings surfaced at top, everything else behind "Advanced", and search.

## Interview angle

**Common questions**
- "This screen feels overwhelming. How would you fix it?"
- "How do you decide what to show and what to hide?"
- "What is progressive disclosure and when is it wrong?"

**Structure for "this screen is overwhelming."** Do not start listing removals. Say:

1. **Identify the primary task.** "First I would confirm what this screen is *for* — what does the user come here to do, and how often?"
2. **Classify the load.** "Then I separate what is inherently complex from what we made complex — jargon, redundant controls, decisions we could default."
3. **Apply, in order:** defaults → grouping → progressive disclosure → removal. Removal last, because removal is the option that loses capability.
4. **Name the cost.** "Hiding advanced options adds a click for power users, so I would check how often those options are actually used before I bury them."

**Advanced move:** mention that you would *measure* rather than assert — SEQ after task, or a time-on-task comparison — and that reduced options can reduce satisfaction for expert users even when it raises novice completion.
