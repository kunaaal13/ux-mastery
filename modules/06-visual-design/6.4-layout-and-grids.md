# 6.4 Layout & Grids

## In one line

A grid is a set of pre-made decisions — its value is not beauty but the elimination of arbitrary variation.

## Grid anatomy

- **Columns** — the vertical divisions. 12 columns is the web default because it divides by 2, 3, 4, and 6.
- **Gutters** — the space between columns.
- **Margins** — the space outside the outermost columns.
- **Rows / baseline grid** — vertical rhythm; often approximated with an 8-point spacing system rather than a strict baseline grid in product work.
- **Breakpoints** — widths at which the layout reconfigures.

## Spacing systems

Use a **4- or 8-point scale** (4, 8, 12, 16, 24, 32, 48, 64). Two benefits: every gap encodes a relationship (Module 04), and handoff becomes unambiguous. Half-steps (2, 6) exist for optical corrections inside components, not for layout.

## Responsive layout

Three distinct strategies, often confused:

1. **Reflow** — the same content, rearranged. Columns stack. Safest default.
2. **Reveal/hide** — different content by viewport. Dangerous: hiding content on mobile assumes mobile users want less, which is usually false. Hide *chrome*, not content.
3. **Restructure** — a genuinely different layout or interaction per platform, e.g. a data table becoming a card list, or a hover-based control becoming a tap-and-sheet.

**Breakpoints should follow the content, not device names.** Set a breakpoint where the layout stops working — where the measure exceeds ~75 characters or a column becomes too narrow — rather than at "iPad width." Device sizes change; content constraints do not.

**Container queries** shift this further: a component can respond to *its own* available width, which is the correct model for design systems, since the same card may sit in a sidebar or a full-width region.

## Composition principles

- **Establish one dominant region.** Most screens have a primary content area; sidebars, headers, and footers are support. Equal-weight regions produce a screen with no entry point.
- **Limit alignment edges** (Module 04) — every new left edge weakens the others.
- **Optical adjustment beats mathematical centring** — icons, arrows, and round glyphs usually need a nudge to look centred.
- **Whitespace is structural, not leftover.** Increase it between groups before you decrease type size to make room.
- **The fold is soft** — scrolling is expected, but attention decays down the page. Put the strongest reason to continue near the top, and ensure the page visibly continues (avoid a full-viewport section that looks like the whole page).

## Density

Density is a product decision (Module 04): consumer products lean spacious, professional tools lean dense because experts trade comfort for simultaneous state. Provide a density setting when you serve both. When increasing density, protect three things: **touch/click target size, contrast, and grouping** — those degrade first and hurt most.

## Layout patterns worth knowing by name

| Pattern | Use |
| --- | --- |
| **Master–detail (list + pane)** | Browsing many items with a persistent detail view; collapses to push navigation on mobile |
| **Dashboard grid** | At-a-glance status; needs deliberate hierarchy or it becomes wallpaper |
| **Feed** | Infinite, chronological or ranked content; needs strong item boundaries and a return-position strategy |
| **Wizard / stepper** | Infrequent branching tasks; poor for frequent, familiar work |
| **Split form + preview** | Configuration with immediate visible consequence |
| **Canvas + inspector** | Direct manipulation with contextual properties; the standard for creative tools |
| **Table with bulk actions** | Data-dense operational work; needs keyboard operability and persistent selection state |

## Applications

**Do this / not that**
- *Not that:* Hiding the filters on mobile because "there is no room."
- *Do this:* Move filters into a bottom sheet with a visible trigger showing the active filter count — the capability stays, the chrome shrinks.

## Interview angle

**Common questions**
- "How do you decide breakpoints?"
- "How would you adapt this desktop screen for mobile?"
- "How do you handle a data table on a phone?"

**Model answer for the table question:** "A table on a phone is usually a restructure problem, not a reflow one. First I would find what the user actually does with the table — scanning for one value, comparing rows, or acting in bulk — because each implies a different mobile form. For scanning, a card list with the two most important fields per item and progressive disclosure of the rest. For comparison, a horizontally scrollable table with a frozen identifying column, which preserves the comparison the table exists for. For bulk operations, selection plus a sticky action bar. What I would avoid is shrinking the type until it fits, which keeps the layout and loses the readability."

That answer starts from the task rather than the layout, which is the point.
