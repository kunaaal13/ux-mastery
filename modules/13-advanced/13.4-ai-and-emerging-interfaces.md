# 13.4 Designing for AI & Emerging Interfaces

## In one line

Classical interface design assumes a deterministic system with a discoverable set of controls; generative systems break both assumptions, so the design problems shift to **capability communication, trust calibration, correction, and authority**.

## What changes

| Classical UI | Generative/probabilistic UI |
| --- | --- |
| Finite, visible controls | Open-ended input; capability is invisible |
| Deterministic output | Variable output for identical input |
| Errors are states | Errors can be fluent, confident, and wrong |
| Consistency is achievable | Consistency is partial at best |
| Undo is well-defined | Actions may have external side effects |

## The core design problems

**1. Capability communication.** Users cannot see the boundary of what the system can do, so they either under-use it (asking only trivial things) or over-trust it. Solutions: concrete example prompts rather than abstract descriptions, capability framing in onboarding, and honest refusal messages that say what *would* work.

**2. Trust calibration.** The goal is not maximum trust; it is *accurate* trust. Over-trust produces unchecked errors; under-trust produces abandonment. Levers: show sources and let users verify, express uncertainty where the system has it, make the reasoning inspectable where useful, and be consistent about failure modes so users can learn them.

**3. Correction and steering.** The interaction is iterative. Editing the previous turn, retrying with a modification, adjusting tone or scope, and pinning constraints must be first-class controls — not a re-typed prompt. The cost of a bad output should be one click, not a restart.

**4. Authority and consequence.** The critical axis is **reversibility**. Automation is safe where actions are cheap to undo and dangerous where they are not. Design for a graduated model: suggest → confirm → act, escalating the confirmation as the blast radius grows. Preview before any external side effect (sending, purchasing, deleting, publishing, running code).

**5. Latency and progress.** Generation is slow relative to the Doherty threshold (Module 03). Streaming output is a genuine improvement because it converts a wait into progress; a stop control is mandatory; and the acknowledgment of the request must still be immediate.

**6. Memory and continuity.** If the system remembers, the user must be able to see what it remembers, correct it, and delete it. Invisible memory is both a trust problem and a privacy problem.

**7. Failure design.** The dominant failure mode is a plausible wrong answer, which classical error handling never had to address. Design the recovery: easy verification paths, clear provenance, an obvious route to a deterministic fallback (a search, a form, a human), and a way to report the failure that visibly changes something.

## Heuristics for AI interfaces

A workable adapted set (see also Module 05.2):

1. Set expectations of capability before the first interaction.
2. Expose uncertainty and provenance.
3. Make correction cheaper than restarting.
4. Preview and confirm anything irreversible or externally visible.
5. Keep the user the initiator of consequential actions.
6. Make memory legible, editable, and deletable.
7. Provide a deterministic escape hatch.
8. Attribute and label generated content honestly.

## Other emerging surfaces

- **Voice / conversational** — no visible affordances, so discoverability is the central problem; error recovery without a screen; confirmation of destructive intents; barge-in support; and designing for ambient, shared, and semi-private contexts.
- **AR / spatial** — occlusion, comfort, safety (a user's attention is partly in the world), session length limits, and social acceptability.
- **Wearables and glanceable UI** — a single decision per glance; notification discipline is the whole design problem.
- **Ambient / IoT** — feedback with no screen, state that changes without the user present, and shared control between household members with different permissions.

## Interview angle

**Common questions**
- "How would you design an AI feature for our product?"
- "How do you handle AI making mistakes?"
- "What is different about designing for AI?"

**Model answer for "what is different":** "Three things. First, capability is invisible — with a normal interface the controls tell you what is possible, and with an open-ended one users have to guess, so I would spend real effort on concrete examples and honest refusals. Second, the failure mode changes: instead of an error state, you get a fluent, confident, wrong answer, so the design work moves into verification, provenance, and cheap correction. Third, the question of authority: I would design a graduated model around reversibility — suggest for anything irreversible, act directly only where undo is trivial — and always preview before an external side effect. Underneath all of it, the goal is calibrated trust rather than maximum trust."

**For "how would you design an AI feature":** resist starting with a chat box. "First I would ask whether the user's job is better served by an open-ended interface or by the model working behind a normal control — a lot of good AI design looks like a better default, a smarter search, or a suggestion inline, not a conversation. Then the same question I would ask for any feature: what is the task, how often, and what does a mistake cost?"
