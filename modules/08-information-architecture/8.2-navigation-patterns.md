# 8.2 Navigation Patterns

## Navigation types

- **Global/primary** — persistent, present on every screen. The product's spine.
- **Local/secondary** — within a section.
- **Contextual/inline** — links inside content, related items.
- **Utility** — account, settings, help, search. Usually visually separated from primary nav.
- **Supplemental** — sitemap, index, guides.
- **Wayfinding** — breadcrumbs, page titles, active states, "you are here" cues.

Wayfinding is the most neglected. Users need to know **where they are, where they can go, and how to get back** at all times.

## Patterns by platform

| Pattern | Best for | Watch out for |
| --- | --- | --- |
| **Top nav bar** | Desktop web, 5–7 destinations | Runs out of space; overflow becomes "More" |
| **Sidebar nav** | Tools with many sections; supports nesting | Consumes horizontal space; collapse needs an obvious signifier |
| **Bottom tab bar (mobile)** | 3–5 top-level destinations, frequent switching | Only for peer destinations, not actions; more than 5 becomes unreadable |
| **Hamburger menu** | Secondary and utility items | Measurably lowers discoverability of what is inside; do not hide primary destinations here |
| **Segmented control / tabs** | Switching views of the same content | Not for navigating to different content types |
| **Drawer/sheet** | Contextual actions and filters | Must be dismissible and reachable by keyboard |
| **Command palette** | Expert users, large action space | Accelerator only, never the sole path |
| **Faceted filtering** | Large catalogues | Must show active filters and result counts; needs an easy clear-all |
| **Breadcrumbs** | Deep hierarchies | Useless in flat structures; must reflect the path, not the history |

**The hamburger question** comes up constantly. The evidence-based answer: hiding navigation behind a menu reduces engagement with the items inside it compared with visible tabs, so put your top 3–5 destinations in a visible bar and use the menu for the tail. On desktop, there is rarely a reason to hide primary navigation at all.

## Search vs. browse

Both, always — but which dominates depends on the user's knowledge:

- **Known-item seeking** ("I want the invoice from March") → search wins.
- **Exploratory seeking** ("what kinds of plans exist?") → browse wins; search is useless if you do not know the vocabulary.
- **Comprehensive seeking** ("all items matching a criterion") → faceted filtering wins.

Search design essentials: forgiving matching (typos, synonyms, plurals), scoped search when the corpus is large, useful zero-result pages (suggestions, popular items, broadened query), visible query in results, and **logging** — zero-result and high-refinement queries are a free, continuous IA research feed.

## Cross-cutting rules

1. **Show current location.** Active states in nav, matching page titles, breadcrumbs in deep structures.
2. **Preserve position on return.** Returning from a detail view to a list should restore scroll position and filters. Losing them is one of the most common and most infuriating defects in feeds and catalogues.
3. **Make back predictable.** In-app back must not conflict with platform back; a modal that traps back is a bug.
4. **Persist state that costs effort** — filters, sort order, selection, drafts — across sessions where sensible.
5. **Nav is not a dumping ground.** Every added item dilutes the rest; adding requires removing or demoting.

## Mobile-specific considerations

- Reachability: primary destinations at the bottom (Fitts + thumb zone, Module 03).
- Gestures as accelerators only (Module 07).
- Deep links must land on a screen with a sensible up-path, not a dead end.
- Notifications are a navigation surface: tapping one must land exactly on the relevant item, not the home screen.

## Interview angle

**Common questions**
- "How many items should the primary nav have?"
- "Would you use a hamburger menu?"
- "How do you handle navigation for a product with 40 features?"

**For the 40-feature product:** "Primary navigation should carry the small number of destinations that cover most sessions, chosen from usage data — not a compressed version of the whole product. The rest becomes a discoverable second layer: a section landing page with grouped links, strong search with synonym support, and contextual entry points at the moment each feature is relevant, which usually outperforms any menu placement. I would validate the structure with a card sort and a tree test before building, and afterwards watch the search-vs-navigate ratio and zero-result queries to see what the structure is failing to surface."
