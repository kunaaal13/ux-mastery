# 10.2 WCAG & Standards

## Structure

WCAG (Web Content Accessibility Guidelines, W3C) is organised as:

**4 principles (POUR)** → **13 guidelines** → **success criteria** (the testable requirements) → techniques (non-normative advice).

**Conformance levels:**
- **A** — minimum; failing these blocks whole populations.
- **AA** — the practical industry and legal target. When someone says "we are WCAG compliant," they almost always mean 2.1 or 2.2 AA.
- **AAA** — enhanced; not expected for entire sites, but worth adopting selectively.

**Versions:** 2.0 (2008), 2.1 (2018, added mobile, low-vision, and cognitive criteria), 2.2 (2023, added focus appearance, target size minimum, dragging alternatives, accessible authentication, and consistent help). WCAG 3.0 is a long-term draft with a different scoring model — do not cite it as a current requirement.

## The criteria you will use most

**Perceivable**
- **1.1.1 Non-text Content (A)** — text alternatives for images. Decorative images get an empty alt so screen readers skip them; informative images describe the information, not the picture.
- **1.3.1 Info and Relationships (A)** — structure conveyed visually must exist in the markup: headings, lists, table headers, and label associations.
- **1.3.5 Identify Input Purpose (AA)** — autocomplete attributes on common fields; helps autofill and cognitive load.
- **1.4.1 Use of Color (A)** — colour is never the only means of conveying information.
- **1.4.3 Contrast (Minimum) (AA)** — 4.5:1 for normal text, 3:1 for large text.
- **1.4.4 Resize Text (AA)** — usable at 200% zoom without loss of content or function.
- **1.4.10 Reflow (AA)** — no two-dimensional scrolling at 320 CSS px width equivalent.
- **1.4.11 Non-text Contrast (AA)** — 3:1 for UI component boundaries and meaningful graphics.
- **1.4.12 Text Spacing (AA)** — content survives user-increased spacing.

**Operable**
- **2.1.1 Keyboard (A)** — all functionality available from a keyboard.
- **2.1.2 No Keyboard Trap (A)** — focus can always leave a component.
- **2.2.1 Timing Adjustable (A)** — time limits can be extended or turned off.
- **2.3.1 Three Flashes (A)** — nothing flashes more than three times per second.
- **2.4.3 Focus Order (A)** — focus order preserves meaning.
- **2.4.4 Link Purpose (A)** — link text makes sense; "click here" repeated 12 times does not.
- **2.4.6 Headings and Labels (AA)** — descriptive.
- **2.4.7 Focus Visible (AA)** — a visible focus indicator. Removing outlines without a replacement is one of the most common and most damaging failures.
- **2.4.11 Focus Not Obscured (AA, 2.2)** — sticky headers must not hide the focused element.
- **2.5.3 Label in Name (A)** — the accessible name contains the visible label text.
- **2.5.7 Dragging Movements (AA, 2.2)** — any drag action has a single-pointer alternative.
- **2.5.8 Target Size (Minimum) (AA, 2.2)** — 24×24 CSS px, with exceptions for spacing and inline text.

**Understandable**
- **3.1.1 Language of Page (A)** — declared, so screen readers use the right pronunciation.
- **3.2.1/3.2.2 On Focus / On Input (A)** — no surprising context change simply from focusing or typing.
- **3.3.1 Error Identification (A)** — errors described in text.
- **3.3.2 Labels or Instructions (A)** — every input has a visible label.
- **3.3.3 Error Suggestion (AA)** — suggest a correction where possible.
- **3.3.7 Redundant Entry (A, 2.2)** — do not make users re-enter information they already provided in the same process.
- **3.3.8 Accessible Authentication (AA, 2.2)** — no cognitive function test (like a memory or transcription puzzle) without an alternative; this is why paste must work in OTP and password fields.

**Robust**
- **4.1.2 Name, Role, Value (A)** — every custom control exposes what it is, what it does, and its state.
- **4.1.3 Status Messages (AA)** — status updates announced without moving focus (live regions).

## Beyond WCAG

- **ARIA** — use only when native semantics cannot do the job. The first rule of ARIA is: do not use ARIA if a native HTML element will do. Bad ARIA is worse than none.
- **Platform guidelines** — Apple's and Android's accessibility guidance covers dynamic type, VoiceOver/TalkBack behaviour, and OS settings you must respect.
- **EN 301 549** — the European standard, which incorporates WCAG and adds requirements for hardware and non-web software.
- **VPAT / Accessibility Conformance Report** — the document enterprise procurement asks for. Knowing what it is signals you have shipped in a serious environment.

## Interview angle

**Common questions**
- "What is WCAG and what level should we target?"
- "Name a few success criteria."
- "What accessibility issues would you check for in this design?"

**Model answer for level:** "AA of WCAG 2.1 or 2.2 is the practical target — it is what regulations and procurement generally reference. AAA is not realistic across a whole product but individual criteria are worth adopting where they matter, like 7:1 contrast for long-form reading. And I would treat conformance as the floor, not the goal — a product can pass every criterion and still be miserable to use with a screen reader, which is why I test the real flows rather than only auditing components."

## Check yourself

1. Name the conformance levels and which is the practical target.
2. State the contrast requirements for text and for UI components.
3. Which criterion is violated by removing focus outlines?
4. What does 2.5.3 Label in Name protect, and for whom?
5. What is the first rule of ARIA?
