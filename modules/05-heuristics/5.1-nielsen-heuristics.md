# 5.1 Nielsen's 10 Usability Heuristics

Jakob Nielsen, 1994 (refined from Nielsen & Molich 1990). They are called *heuristics* rather than rules because they are broad rules of thumb, not specifications. They remain the industry's default evaluation vocabulary — knowing all ten by name, with an example violation and a fix for each, is a baseline interview expectation.

---

## 1. Visibility of System Status

**Statement:** the system should always keep users informed about what is going on, through appropriate feedback within reasonable time.

**Violations:** a button that does nothing visible when tapped; an upload with no progress; no indication of which filter is active; a saved/unsaved state that is invisible; no confirmation that a message sent.

**Fixes:** immediate acknowledgement of every action (<100 ms), determinate progress for anything over ~4 s, persistent state indicators (selected filters as removable chips), explicit save state ("All changes saved").

**Connects to:** Doherty Threshold, Gulf of Evaluation.

---

## 2. Match Between System and the Real World

**Statement:** speak the users' language, with familiar words, phrases, and concepts, following real-world conventions and a natural, logical order.

**Violations:** internal jargon in the UI ("Entity resolution failed"); error codes with no meaning; icons that represent database concepts; date order that mismatches locale; a settings taxonomy that mirrors the backend services.

**Fixes:** use the users' words (gathered in research, not invented in a meeting), name things after goals not systems, order steps the way the task happens in the world, validate labels with a first-click test.

**Connects to:** mental models, Jakob's Law.

---

## 3. User Control and Freedom

**Statement:** users often perform actions by mistake and need a clearly marked "emergency exit."

**Violations:** no undo; no back; a wizard you cannot exit without losing everything; an autoplaying video with no pause; a modal with no dismiss; irreversible bulk actions.

**Fixes:** undo as the default safeguard (usually better than a confirmation dialog, which users learn to click through); cancel on every flow; preserve entered data when a user backs out; make destructive actions reversible for a window rather than merely confirmed.

**Connects to:** Postel's Law (accept the messy real case), error recovery.

---

## 4. Consistency and Standards

**Statement:** users should not have to wonder whether different words, situations, or actions mean the same thing. Follow platform and industry conventions.

**Two kinds:**
- **Internal consistency** — within your product. Violations are the most damaging, because your users learn *you*.
- **External consistency** — with the platform and category. This is Jakob's Law expressed as a heuristic.

**Violations:** three different date formats in one product; "Delete" here and "Remove" there for the same operation; a non-standard back gesture; primary button on the left in one flow and the right in another.

**Fixes:** a design system with content guidelines, not just components; a terminology glossary; platform-native controls unless there is a strong reason otherwise.

---

## 5. Error Prevention

**Statement:** better than good error messages is a careful design that prevents problems in the first place.

**Two error types (Norman):**
- **Slips** — the user intended the right thing but executed it wrong (typo, mis-tap). Prevent with constraints, larger targets, forgiving input, and undo.
- **Mistakes** — the user's intention was wrong, from a faulty mental model. Prevent with clearer models, better labels, and confirmation *with meaningful context*.

**Fixes:** constrain rather than validate (date pickers over free text); disable impossible actions and say why; use structured inputs; require confirmation only for irreversible, high-cost actions and make that confirmation informative ("This deletes 1,240 records") rather than generic ("Are you sure?").

---

## 6. Recognition Rather Than Recall

**Statement:** minimise memory load by making objects, actions, and options visible.

**Violations:** icon-only toolbars for occasional-use tools; codes that must be carried across steps; a confirmation page that does not show what was entered; hidden filters; commands only accessible via memorised syntax.

**Fixes:** icon + label; visible recent items; show entered values at confirmation; persistent breadcrumbs; autocomplete; a command palette *in addition to* visible UI, not instead of it.

**Connects to:** Miller's Law, memory (Module 02.4).

---

## 7. Flexibility and Efficiency of Use

**Statement:** accelerators — unseen by the novice — may speed up interaction for the expert, so the system can cater to both.

**Violations:** no keyboard shortcuts in a tool used all day; no bulk actions; no saved views; forcing experts through a wizard designed for first-timers.

**Fixes:** keyboard shortcuts and a command palette; bulk selection; saved filters and templates; recent/frequent items; allow tailoring of frequent actions. The design goal is **layering**: the novice path stays visible, the expert path is available but not in the way.

---

## 8. Aesthetic and Minimalist Design

**Statement:** interfaces should not contain information that is irrelevant or rarely needed; every extra unit of information competes with the relevant units and diminishes their visibility.

Note the actual claim: it is about **competition for attention**, not about being visually sparse. A dense professional tool can satisfy this heuristic if everything present is relevant.

**Violations:** promotional banners inside a task flow; five calls to action on one screen; repeated help text; decorative imagery that pushes content below the fold.

**Fixes:** the element-justification checklist (does it enable an action, communicate state, provide required information, or aid comprehension?); progressive disclosure; one primary action per view.

---

## 9. Help Users Recognise, Diagnose, and Recover from Errors

**Statement:** error messages should be in plain language, precisely indicate the problem, and constructively suggest a solution.

**A good error message has four parts:**
1. **What happened** — in the user's terms, not the system's
2. **Why** — enough cause to make it make sense
3. **How to fix it** — a specific, actionable next step
4. **A way out** — a button, a link, a retry, or a contact route

**Violations:** "An error occurred"; "Invalid input"; a red field with no explanation; errors that clear the form; error text that blames the user.

**Fixes:** field-level, adjacent, specific messages; preserve user input; state constraints *before* submission ("8+ characters") rather than only after failure; never use only colour to mark the error (Module 10); write in the same voice as the rest of the product.

---

## 10. Help and Documentation

**Statement:** ideally the system needs no documentation, but it may be necessary to provide help, focused on the user's task, listing concrete steps, and not too large.

**Violations:** a help centre link as the only support; documentation that describes the UI rather than the task; search that returns marketing pages; no help at the point of confusion.

**Fixes:** contextual, in-place help at the moment of doubt; task-oriented articles ("Transfer money to a new payee"), not feature-oriented ones ("The Payees screen"); searchable and versioned; measure which help articles are read, because each one is a usability defect with a URL.

---

## Using the ten in practice

They overlap by design. A single problem may violate three heuristics — that is normal, and citing the most explanatory one is enough. In a critique, always pair **heuristic + observed consequence + fix**:

> "The active filters are not shown anywhere after the panel closes — a visibility-of-system-status violation. Users re-open the panel to check, and some conclude filtering did not apply. Fix: show active filters as removable chips above the results."

That three-part shape is the difference between a critique that sounds trained and one that sounds like an opinion.
