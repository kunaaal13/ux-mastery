# 5.2 Other Heuristic Sets

Nielsen's ten are the default vocabulary, but they are not the only set, and knowing a second one signals depth.

---

## Shneiderman's Eight Golden Rules of Interface Design

Ben Shneiderman, *Designing the User Interface*. More operational than Nielsen's, and stronger on interaction mechanics.

1. **Strive for consistency** — in sequences of actions, terminology, layout, and colour.
2. **Seek universal usability** — recognise diverse users: novices vs experts, ages, abilities, technology diversity. Provide shortcuts for experts and explanations for novices.
3. **Offer informative feedback** — proportional to the action: modest for frequent minor actions, substantial for infrequent major ones.
4. **Design dialogues to yield closure** — sequences of actions should have a beginning, middle, and clear end, with feedback that signals completion. (Connects to Zeigarnik and Peak–End.)
5. **Prevent errors** — and provide simple, constructive, specific recovery.
6. **Permit easy reversal of actions** — relieves anxiety and encourages exploration.
7. **Keep users in control** — users should be the initiators of actions, not the responders. Avoid surprising system-initiated changes.
8. **Reduce short-term memory load** — keep displays simple, consolidate multi-page displays, provide sufficient training time for codes and sequences.

**Where it adds value over Nielsen:** rule 2 (universal usability, which pre-figures accessibility and expertise layering), rule 3 (feedback should be *proportional*, a nuance Nielsen's #1 lacks), and rule 4 (closure as an explicit design goal).

## Tognazzini's First Principles of Interaction Design

Bruce "Tog" Tognazzini's set is longer and more opinionated. The ones worth knowing:

- **Anticipation** — bring to the user everything needed at each step; do not make them go hunting.
- **Discoverability** — a fair proportion of functionality should be findable without documentation.
- **Explorable interfaces** — give users well-marked roads and landmarks, and make exploration safe (reversible).
- **Fitts's Law** — included as a first principle, which tells you how central motor cost is to interaction quality.
- **Latency reduction** — acknowledge input immediately; use multi-threading so the interface never blocks.
- **Protect users' work** — never lose data. Ever. This is the highest-severity failure class in almost any product.
- **Readability** — text must be legible for the actual population, including older users; do not sacrifice legibility to style.
- **Simplicity vs. featurism** — feature count is not value.

## Domain-specific heuristic sets

Heuristics can and should be adapted. Well-known specialisations:

- **Mobile/touch:** thumb reachability, target size, gesture discoverability, interruption tolerance, offline behaviour.
- **Data-dense/enterprise:** density appropriateness, bulk operations, keyboard operability, state persistence across sessions, error tolerance in long-running work.
- **Voice/conversational:** turn-taking, error recovery without a screen, discoverability of capability, confirmation of destructive intents, barge-in support.
- **Games:** feedback juiciness, difficulty ramp, agency, learnability by play rather than instruction.
- **AI/LLM interfaces:** setting expectations of capability, exposing uncertainty, allowing correction and steering, showing sources, making the cost of a mistake visible, and offering an easy path to a deterministic fallback.

Writing a custom heuristic set for a product domain — 6 to 10 items, each with a rationale — is a strong senior-level artifact and a common take-home exercise.

## Choosing a set

| Situation | Use |
| --- | --- |
| General evaluation, shared vocabulary with a team | Nielsen's 10 |
| Interaction mechanics, expert/novice balance | Shneiderman's 8 |
| Deep interaction critique, motor and latency issues | Tognazzini |
| Explaining *why* a control confuses people | Norman's principles |
| A specialised domain | An adapted set, written down and agreed before the evaluation |

## Interview angle

**Question:** "What frameworks do you use to evaluate a design?"

Strong answer: "Nielsen's ten as the default, because it is shared vocabulary — everyone in the room recognises the terms, which makes findings actionable rather than debatable. I lean on Shneiderman when the problem is interaction mechanics, particularly the ideas that feedback should be proportional to the action and that dialogues should yield closure. And for a specialised product I would write an adapted set up front — for a voice interface, half of Nielsen's heuristics do not apply cleanly and things like barge-in and confirmation of destructive intents matter far more."

That answer shows you use frameworks as tools rather than as recitation.
