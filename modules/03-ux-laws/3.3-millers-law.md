# 3.3 Miller's Law

## In one line

People can hold about seven (± two) *chunks* in short-term memory — and the practical lesson is about chunking, not about the number seven.

## Basic

George Miller, 1956, "The Magical Number Seven, Plus or Minus Two." The paper was about the span of absolute judgement and immediate memory. Its most useful idea is **chunking**: memory span is measured in meaningful units, and grouping raw items into meaningful units increases how much you can hold.

`0 8 0 0 1 2 3 4 5 6 7` is eleven items. `0800 123 4567` is three.

## Deeper

### The misuse

"Miller's Law says menus should have 7±2 items" is the most-repeated wrong statement in UX. Miller never said that, and navigation is not a short-term memory task — the items are on screen, so nothing is being held in memory. Menu length is governed by visual search and information scent, not memory span.

Modern working-memory research suggests **~4 chunks** for unrelated items under realistic conditions. If you are going to cite a number, cite four and say why the difference exists.

### Where the law genuinely applies

Any moment the interface *removes* information the user still needs:

- Multi-step forms that ask you to remember a code from step 1 at step 4
- One-time passcodes delivered in an app you must leave to read
- Comparison tables that scroll the header row out of view
- Instructions in a modal that disappears before the task
- Error messages that vanish before the user reaches the field

The general rule: **do not make memory a load-bearing part of the design.**

### Chunking as a design technique

| Raw | Chunked |
| --- | --- |
| 16-digit card number | 4 groups of 4 |
| 30-field form | 5 sections of 6, with headers |
| 25-item settings list | 5 labelled groups |
| A long paragraph of instructions | A numbered list of 4 steps |

Chunk boundaries must be **meaningful**, not arbitrary — grouping unrelated fields under one header creates a false model and hurts.

## Applications

- **OTP inputs split into 6 separate boxes** — visual chunking, plus it makes position errors obvious.
- **Sticky table headers** — remove the memory requirement while scrolling.
- **Persistent order summary in checkout** — the user never has to remember what they are buying.
- **"Copy code" buttons** — eliminate the transcription task entirely, which is better than supporting it.

**Do this / not that**

- *Not that:* A confirmation dialog that says "Type the project name to confirm" while hiding the project name.
- *Do this:* Show the name adjacent to the field. The confirmation is still deliberate; it is just not a memory test.

## Interview angle

**Common questions**
- "How many items should a navigation menu have?" (Often a trap.)
- "What is Miller's Law?"

**The trap answer.** If you say "7±2, so seven items," you have failed the follow-up. The strong answer: "Miller's finding was about short-term memory span in chunks, not about menu length — items in a menu are visible, so memory is not the constraint. Menu length should be driven by the task structure, information scent, and scanning cost. Where Miller genuinely applies is any point where I remove information the user still needs — codes across steps, headers scrolling away, values that must be transcribed."

That reframe is one of the highest-value single answers in a UX interview, because interviewers use this exact question to separate memorisers from practitioners.

## Check yourself

1. What was Miller's 1956 paper actually about?
2. Give a more defensible modern number for working memory, and explain the discrepancy.
3. Why is "menus should have 7±2 items" wrong?
4. Name three interface situations where Miller's Law genuinely applies.
5. What makes a chunk boundary good rather than arbitrary?
