# 7.4 Forms & Inputs

## In one line

Forms are where most products lose most of their users, and almost every form problem has a known, cheap solution.

## Structure

- **One column.** Multi-column forms cause skipped fields because the eye's path becomes ambiguous. Exceptions: genuinely paired short fields (city/postcode, expiry/CVC).
- **Labels above fields.** Fastest to scan (a single vertical path), works best on mobile, and does not truncate in longer languages. Left-aligned labels save vertical space but slow completion.
- **Never use placeholders as labels.** The label disappears exactly when it is needed, it fails contrast requirements at typical styling, it breaks screen-reader association, and it makes review impossible before submit. Placeholders are for *format examples*, if used at all.
- **Group into meaningful sections** with headers (chunking, Module 03), and make between-group spacing clearly larger than within-group (Gestalt, Module 04).
- **Field length signals expected input.** A postcode field the width of the page is a lie about what is expected.
- **Ask for the minimum.** Every field costs completion. For each one, ask: do we need this *now*, do we need it at all, and can we derive it?

## Order and progression

- **Easy and low-risk first** (goal-gradient, Module 03), sensitive and effortful later. But keep a logical order the user recognises; do not scramble a familiar sequence for motivation.
- **Do not ask for anything requiring a physical document until the user has committed** — passport numbers before a price is shown is a classic abandonment cause.
- **Multi-step vs. single page:** steps for long, branching, infrequent tasks (with a stepper showing progress and remaining count); single page for short, familiar ones. Preserve data across steps and allow going back without loss.

## Validation

The ordered priority (also a reusable interview answer):

1. **Prevent** — constraints, structured pickers, input masks, sensible defaults, and disabling impossible combinations.
2. **Accept liberally** (Postel, Module 03) — strip spaces and dashes, trim whitespace, accept multiple formats, normalise, and echo back the interpretation.
3. **Validate at the right moment** — on blur for format errors, not on every keystroke (which punishes users mid-typing), and never only on submit. Positive validation ("looks good") is optional and can reassure on long forms.
4. **Explain** — adjacent, specific, in the user's words, stating what is wrong *and* what would be right. Show constraints (e.g. password rules) before entry, not after failure.
5. **Recover** — preserve every entered value, move focus to the first error, summarise errors at the top with links, and never clear the form.

Accessibility requirements that also improve usability for everyone: associate labels programmatically, mark errors with text and icon rather than colour alone, announce errors to assistive technology, and keep the error message reachable from the field.

## Input selection

| Data | Right control | Why |
| --- | --- | --- |
| 2 mutually exclusive options | Segmented control or radios | Both options visible; no hidden state |
| 3–5 exclusive options | Radios | Visible; comparison is possible |
| 6+ exclusive options | Select, or typeahead if long | Space, and search collapses the set |
| Boolean, applies immediately | Toggle | Signals an immediate state change |
| Boolean, applies on submit | Checkbox | Signals a pending choice |
| Date | Picker + typed entry | Pickers prevent format errors; typed entry is faster for distant dates |
| Many from a set | Multi-select with chips | Selections stay visible |
| Free text with known values | Combobox / typeahead | Speed plus consistency |

**Toggle vs. checkbox** is a common interview probe: a toggle implies the change takes effect immediately; a checkbox implies it is applied when the form is submitted. Using a toggle inside a form with a Save button is a mismatch users notice as ambiguity.

## Mobile specifics

- Set the correct keyboard type (`inputmode`, `type`) — numeric for numbers, email for emails. Free.
- Enable autofill and autocomplete attributes; autofill is the single largest completion improvement available and costs nothing.
- Touch targets ≥44 pt with adequate spacing.
- Avoid fields that require switching apps mid-flow (e.g. OTP) — support autofill of one-time codes.

## Applications

**Do this / not that**
- *Not that:* "Password must be 8+ characters with one uppercase, one number, and one symbol" shown only after a failed submit.
- *Do this:* Show the rules before typing, validate them live as satisfied criteria tick off, and accept a long passphrase rather than forcing symbol gymnastics.

## Interview angle

**Common questions**
- "How would you improve this form's completion rate?"
- "Toggle or checkbox?"
- "How do you handle validation?"

**Model answer for completion rate** — attack it in this order and name the trade-offs: (1) remove fields — the biggest lever, since every field costs completion; (2) enable autofill and correct keyboards; (3) fix validation timing and messages, preserving input on error; (4) reorder so effortful and document-requiring fields come after commitment, noting the data-quality risk of front-loading easy fields; (5) show progress and allow save-and-resume for long forms; (6) instrument field-level drop-off and error rates so the next change is evidence-driven rather than another guess.

Ending with instrumentation is what turns a list of best practices into a plan.
