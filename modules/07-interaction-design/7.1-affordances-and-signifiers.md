# 7.1 Affordances & Signifiers

## In one line

An affordance is what an object *can* do; a signifier is what tells the user it can do it — and interfaces fail far more often on signifiers than on affordances.

## The distinction

Don Norman borrowed "affordance" from J.J. Gibson, then spent years correcting its misuse. The precise version:

- **Affordance** — a relationship between an object's properties and an agent's capabilities. A chair affords sitting *for a human*. A flat plate on a door affords pushing.
- **Perceived affordance / signifier** — the perceptible signal that communicates where and how to act. The "PUSH" sign, the visual styling of a button, the underline on a link.

In a digital interface, **almost everything is a signifier**, because pixels afford nothing physically. A button is not "clickable" by nature; it is clickable because the software says so, and it *looks* clickable because we have learned a visual convention (Jakob's Law).

**The practical consequence:** when users cannot find a control, the fix is almost never more capability — it is a stronger signifier.

## Norman's design principles

| Principle | Definition | Interface examples |
| --- | --- | --- |
| **Affordance** | What actions are possible | Draggable card, tappable row |
| **Signifier** | What communicates that possibility | Drag handle, chevron, button styling, cursor change, "swipe" hint |
| **Mapping** | Relationship between control and effect | Volume slider going up for louder; a stove's knob layout matching burner layout |
| **Feedback** | Confirmation that something happened | Pressed state, toast, item appearing in list |
| **Constraints** | Limits on possible actions | Disabled dates, max length, structured pickers |
| **Consistency** | Same thing looks and behaves the same | Same button style for the same action class |
| **Conceptual model** | The story the design tells (Module 02.1) | "Files in folders", "cards in a deck" |

**Natural mapping** is worth dwelling on: the best control layouts are spatially analogous to what they control. Norman's canonical example is a stove where the knobs are arranged like the burners, so no labels are needed. In software: a layer panel ordered top-to-bottom matching visual stacking, or a brightness slider that goes right for brighter.

## Discoverability failures

The commonest real-world interaction bugs:

1. **Invisible gestures.** Swipe-to-delete, long-press menus, and pull-to-refresh have no signifier at all — they are learned externally or not at all. Rule: **a gesture may be an accelerator, never the only path** to an action.
2. **Flat design without cues.** Removing shadows and borders removed the signifiers that distinguished interactive from static. The fix is not skeuomorphism; it is a consistent, learnable convention *within* the product (colour + weight + spacing pattern reserved for interactive elements).
3. **Hover-only affordances.** Controls that appear on hover are invisible on touch and to keyboard users. If it appears on hover, it must also be reachable another way.
4. **Ambiguous icons.** An icon alone is a recall test with no answer key. Icon + label is the default; icon-only is acceptable only for a small set of near-universal symbols (close, search, back, play) in a high-frequency context.
5. **Falsely disabled controls.** A disabled button with no explanation is a dead end — the user cannot tell what to change. Prefer an enabled control that explains the blocker on activation, or a disabled control with adjacent text stating the requirement.

## Constraints as design

Constraints prevent errors *before* they happen (heuristic #5). Four kinds Norman names:

- **Physical** — impossible to do (a plug that only fits one way; a slider bounded at both ends).
- **Cultural** — conventions people have learned (red means stop).
- **Semantic** — meaning-based (a rider faces forward on a motorbike).
- **Logical** — deduction from the situation (one piece left, one hole left).

In interfaces: date pickers instead of text fields, max-length inputs, structured selectors, disabled invalid combinations, and defaults that make the common case require no action. Every constraint you add removes a class of error permanently — cheaper than any error message.

## Applications

**Do this / not that**
- *Not that:* A row that opens a detail view on tap, with no chevron, no hover state, and no cursor change.
- *Do this:* Chevron on the right, hover/press states, pointer cursor, keyboard focus ring, and the whole row as the hit area (Fitts's Law).

**Example — mapping done well.** A seat-selection map that mirrors the physical aircraft layout requires no legend for orientation. A seat picker listed as "Row 14, Seat C" in a dropdown makes the user reconstruct the mapping in their head.

## Interview angle

**Common questions**
- "What is the difference between an affordance and a signifier?"
- "Users cannot find feature X. What do you do?"
- "Is it ever okay to hide functionality behind a gesture?"

**Answering the gesture question well:** "Gestures are accelerators, not primary paths. They have no signifier, so discoverability is near zero without teaching, and they exclude keyboard and assistive-technology users entirely. I would ship the gesture *and* a visible control — swipe-to-delete plus a visible action in an overflow menu — and I would measure whether the gesture ever gets adopted before considering it as anything other than a shortcut."

**For "cannot find feature X":** run the discoverability checklist — is there a signifier at all, is it in the user's path at the moment of need, does its label match the user's words (heuristic #2), is it hover-only, is it buried below a fold or inside an overflow menu, and does the entry point sit where the mental model predicts. Then say you would verify with a first-click test rather than guessing.
