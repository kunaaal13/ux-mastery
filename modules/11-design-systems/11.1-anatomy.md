# 11.1 Anatomy of a Design System

## In one line

A design system is the shared, versioned set of decisions — tokens, components, patterns, and guidance — that lets many people produce consistent work without renegotiating every choice.

## The layers

**1. Foundations / design tokens**
The atomic decisions, named and versioned: colour, typography, spacing, radius, elevation, motion durations and easings, breakpoints, z-index scale.

- **Primitive tokens** — raw values: `blue-600`, `space-4`.
- **Semantic tokens** — role-based: `color-text-primary`, `color-surface-raised`, `color-border-danger`. Components consume these, never primitives.
- **Component tokens** — optional third tier scoped to a component: `button-primary-background`.

Semantic tokens are what make theming, dark mode, brand variants, and accessibility modes possible without touching component code (Module 06.3).

**2. Components**
Reusable interface elements with defined props, states, and behaviour. Each needs: anatomy, variants, all states (Module 07.2), content guidelines, accessibility specification (Module 10.3), do/don't examples, and a clear statement of *when not to use it*.

**3. Patterns**
Compositions that solve recurring problems: forms, empty states, error handling, page templates, navigation, data tables, filtering, onboarding. Patterns are where a system creates the most consistency, and they are the layer most systems neglect in favour of shipping more components.

**4. Guidelines**
Voice and tone, content style, accessibility standards, layout and density rules, iconography rules, motion principles, and the decision rules the system encodes.

**5. Tooling and infrastructure**
The design library (Figma), the code library, token pipeline, documentation site, versioning, changelog, contribution process, and linting or CI checks that prevent drift.

## Atomic Design (Brad Frost)

Atoms → Molecules → Organisms → Templates → Pages.

Useful as a **mental model for composition**; frequently unhelpful as a literal folder structure, because arguments about whether something is a molecule or an organism consume time and produce nothing. Take the hierarchy, skip the taxonomy debate.

## What makes a component good

- **The right level of abstraction.** Too specific and it is used once; too generic and every use site reimplements the meaning. A good test: could a new team member use it correctly from the documentation alone?
- **States complete** — including focus, error, loading, disabled, and empty.
- **Accessible by default.** The consumer should not need to know ARIA to use it correctly. This is the single biggest multiplier a system provides.
- **Composable rather than configurable.** Twenty boolean props is a smell; slots and composition scale better than flags.
- **Documented with the "when not to use"** section — this prevents the most common misuse.
- **Content guidance included** — button label conventions, sentence case, character limits, and what happens when text overflows.

## Design–code parity

The system is only useful if the design library and the code library agree. Practices that keep them aligned:
- One source of truth for tokens, generated into both platforms (Style Dictionary or similar).
- Naming identical across design and code.
- Component versions released together with a changelog.
- Periodic audits comparing production screens against the library.
- Code Connect or equivalent mapping so designers and engineers reference the same component identity.

Drift is inevitable; the question is whether you detect it in weeks or in years.

## Interview angle

**Common questions**
- "What makes a good design system?"
- "How do you decide what belongs in the system?"
- "Tokens — why bother?"

**For "what belongs":** "The test is repetition plus stability. Something used in three or more places, whose behaviour is settled, belongs in the system. Something used once, or still changing weekly, belongs in the product until it settles — promoting it early creates churn for every consumer. I would rather have thirty components everyone trusts than a hundred that are half-right, because the cost of an unreliable system is that people stop using it and consistency is worse than before it existed."

**For tokens:** "They decouple decisions from usage. With semantic tokens, dark mode, a high-contrast mode, and a white-label brand are remappings rather than rewrites, and I can audit misuse — a `danger` token on a neutral border is visible in review, while `#D93025` is not."

## Check yourself

1. Name the five layers of a design system.
2. Give the three tiers of tokens and say which components should consume.
3. Which layer do most systems neglect, and what is the cost?
4. What is the test for whether something belongs in the system?
5. Why is "accessible by default" the biggest multiplier a system provides?
